## 背景

在 Windows OpenSSH 環境中，金鑰已被複製到遠端，不代表伺服器實際接受該金鑰。此外，將適用於 Unix 殼層或互動式桌面的假設直接套用到 Windows 遠端工作階段，常會造成誤判。

## 解決方案

### 確認系統實際讀取的授權金鑰檔

Administrators 群組帳號通常會符合 `sshd_config` 中的 `Match Group administrators` 規則，因此讀取的是標準系統路徑 `C:\ProgramData\ssh\administrators_authorized_keys`，而不是個人目錄下的 `authorized_keys`。

該系統金鑰檔的存取控制清單應限制為 `SYSTEM` 與 `Administrators`，避免權限過寬導致 OpenSSH 拒絕使用檔案，也避免不必要的寫入權限。

### 驗證伺服器是否真正接受金鑰

`ssh-copy-id` 顯示金鑰已加入，只能證明寫入步驟看似完成，不能證明登入時已成功採用金鑰。應停用互動式密碼後再測試：

```text
ssh -o BatchMode=yes -o PasswordAuthentication=no <連線目標>
```

若仍失敗，使用 `ssh -vvv` 檢視詳細記錄，明確區分用戶端「已提出」金鑰與伺服器「已接受」金鑰。這可避免把密碼後援登入誤認為金鑰驗證成功。

### 避免錯誤的遠端執行假設

針對 Windows 遠端執行 Unix 殼層探測，可能出現 `exec`、`[` 相關錯誤或亂碼。這類輸出通常反映遠端殼層與命令語法不相容，不宜直接解讀為應用程式本身故障。

GUI 程式由 SSH 背景工作階段啟動時，也不保證會顯示在目前的互動式桌面。若要改用互動式排程，必須先取得明確同意，因為建立排程屬於持久性系統變更；測試完成後也必須移除相關排程，避免留下非預期狀態。

### 連續失敗時縮小診斷範圍

同一工具或命令連續失敗後，不應持續盲目重試。應先蒐集最小且足以判斷問題的證據，例如：

- 實際套用的授權金鑰檔位置。
- 金鑰檔的存取控制清單是否符合要求。
- 無密碼後援模式下的登入結果。
- `ssh -vvv` 中金鑰被提出與被接受的關鍵事件。
- 遠端工作階段使用的命令環境，以及是否需要互動式桌面。

## 經驗總結

- Administrators 群組帳號應優先檢查系統層級的授權金鑰檔與其權限。
- 金鑰已寫入不等於驗證成功，必須停用密碼後援進行測試。
- 詳細 SSH 記錄的重點是區分金鑰被提出與被接受。
- 遠端命令與 GUI 行為取決於 Windows 工作階段語意，不能沿用 Unix 或互動式桌面假設。
- 涉及互動式排程等持久性變更時，須先取得明確同意並在完成後清理。
- 重複失敗時應改採最小證據導向的診斷流程。

## 相關工具與方法

- `ssh-copy-id`：只用於判斷金鑰寫入步驟，不作為驗證成功的依據。
- `ssh -vvv`：檢查金鑰提出與接受流程。
- 批次模式與停用密碼驗證：確認登入是否純粹依賴金鑰。

# TeamAI 工作經驗整理與分享

## 目的

把一次工作的上下文與解法，轉換成團隊可以搜尋、重複使用、持續改善的知識。核心循環是：

```text
實際工作
  ↓
Learning：記錄一次問題與經驗
  ↓ 反覆驗證、方法穩定
Skill：整理成可執行的工作流程
  ↓ 團隊必須遵守
Rule：整理成固定規範
```

TeamAI 的 `learning` 適合保存解法與經驗；`skill` 適合保存步驟化流程；`rule` 適合保存不可違反的團隊原則。不要把三者混成一篇沒有用途的長日記。

## 觸發時機

使用本 skill 的情境包括：

- 使用者要求整理剛才的工作經驗、心得、踩坑或解法。
- 使用者要求把工作方法分享給團隊。
- 解決了複雜的 bug、部署問題、環境問題或整合問題。
- 發現一個之後可以重複使用的流程、模式或最佳實務。
- 使用者想把既有 learning 升級成 skill 或 rule。
- 工作前需要搜尋團隊過去的相關經驗。

## 工作流程

### 1. 先確認既有知識

如果任務與過去的工作可能相關，先執行：

```powershell
teamai recall status
teamai recall <關鍵字>
```

若 recall 已啟用，AI 工具會在支援的工作階段自動搜尋；仍要以目前檔案、實測結果和最新狀態為準，不能盲目套用歷史 learning。

### 2. 從工作內容萃取事實

只記錄已確認的內容，至少整理：

- **背景**：當時要完成什麼工作？
- **症狀**：看到了什麼錯誤、限制或異常行為？
- **原因**：如何確認根本原因？區分事實與推測。
- **決策**：有哪些方案？為什麼選目前方案？
- **解法**：可重現的步驟、命令、檔案或設定。
- **驗證**：做了哪些測試，結果如何？
- **陷阱**：下次最容易踩到什麼坑？
- **適用範圍**：何時適用、何時不適用？

不要寫入密碼、token、API key、cookie、私人資料或未授權的內部機密。必要時以 `<REDACTED>` 或泛化名稱取代。

### 3. 判斷要建立哪一種資源

| 判斷 | 資源 | 適合內容 |
|---|---|---|
| 單次問題但解法值得查詢 | learning | 問題、原因、解法、驗證與踩坑 |
| 已驗證且會反覆執行 | skill | 前置條件、步驟、分支、檢查與完成標準 |
| 團隊每次都必須遵守 | rule | 強制規範、禁止事項與例外處理 |
| 穩定的系統背景知識 | doc | 架構、環境、API、產品說明 |

若尚未有足夠證據，不要過早把一次偶然的解法寫成 rule；先建立 learning，日後再升級。

### 4. 產生 learning 文件

文件必須使用 Markdown，開頭包含 YAML frontmatter：

```markdown
---
title: "<簡短且可搜尋的標題>"
author: <TeamAI username>
date: <YYYY-MM-DD>
tags: [技術標籤, 問題類型, workflow]
---

## 背景
描述當時要完成的工作與遇到的問題。

## 根本原因
說明如何確認原因；不確定的部分要明確標示。

## 解決方案
列出可重現的步驟與必要命令。

## 驗證結果
說明實際執行的檢查與結果。

## 經驗與踩坑
- 可重複使用的經驗。
- 下次要避免的錯誤。

## 何時升級成 Skill 或 Rule
說明若未來反覆遇到此情境，應如何整理成 skill 或 rule。

## 相關 Skills
- <相關 skill 名稱>
```

標題要能直接表達核心問題；tags 使用 2–5 個有意義的標籤，例如 `docker`、`deployment`、`troubleshooting`、`workflow`、`best-practice`。

### 5. 先讓使用者確認，再發布

先把整理結果呈現給使用者。只有使用者明確要求發布、分享或確認可以發布時，才執行：

```powershell
teamai contribute --file <文件路徑> --title "<文件標題>"
```

`teamai contribute` 是發布 learning 的流程，不要用 `teamai push` 取代它。`teamai push` 是發布既有 skill、rule 或 doc 資源的流程。

### 6. 發布後驗證

```powershell
teamai status
teamai recall <相關關鍵字>
teamai doctor
```

提醒使用者：其他成員通常需要執行 `teamai pull`，或等待下一個支援 hooks 的 AI 工作階段，才會取得新的團隊知識。

## 將 learning 升級成 skill

當同一類問題反覆出現，或解法已經經過多次驗證時，建立一個具體名稱的 skill。skill 至少應包含：

1. 觸發條件與不適用情況。
2. 前置條件與安全檢查。
3. 按順序排列的操作步驟。
4. 失敗分支與停止條件。
5. 驗證方法與成功標準。
6. 不可暴露或不可自動化的敏感操作。

完成後，先使用 `teamai status` 檢查，再透過：

```powershell
teamai push --skill "<skill 路徑>"
```

發布給團隊。發布前必須確認內容沒有 secrets，也沒有把未驗證的推測寫成保證。

## 將 learning 升級成 rule

只有在團隊已經明確同意、內容穩定且確實需要一致遵守時，才建立 rule。Rule 應該短、明確、可檢查，並列出必要例外；不要把完整操作手冊塞進 rule。

## 輸出要求

完成整理時，用繁體中文回報：

1. 本次 learning 的標題。
2. 核心問題與解法摘要。
3. 驗證證據。
4. 是否建議升級成 skill 或 rule。
5. 是否已發布；若未發布，明確說明等待使用者確認。
6. 實際建立或發布的檔案路徑與命令結果。

## 限制與注意事項

- 不要自動保存完整對話；只萃取與任務相關、已驗證且可重用的內容。
- 不要把個人機密、憑證、token 或私人資料寫入 learning、skill、rule 或 team repo。
- 不要把歷史 learning 當成目前環境的真相；先重新檢查現況。
- 不要在使用者未確認時發布內容。
- 不要聲稱已分享，除非 `teamai contribute` 或 `teamai push` 實際成功。

## 驗證

- 文件有合法 YAML frontmatter，且 title、author、date、tags 齊全。
- 內容同時包含背景、原因、解法、驗證、踩坑與適用範圍。
- 已掃描並移除 secrets 與私人資料。
- 發布後 `teamai status` 與 `teamai doctor` 沒有新增錯誤。
- 能用 `teamai recall <關鍵字>` 找回已發布的 learning。
